# 定制开发规则

## 1. 功能集中放置

| 内容 | 归属 | 约定 |
| --- | --- | --- |
| 后端功能 | `extensions/<feature>/` | handler、service、repository、model 按实际复杂度在功能内组织，简单功能无需建空层级 |
| 前端功能 | `web/src/extensions/<feature>/` | 组件、hooks、状态、API 调用、工具和私有样式随功能放置 |
| 共享定制配置 | `extensions/config/`、`web/src/extensions/config/` | 有共享需求时再创建，功能私有配置留在功能目录 |
| 前端定制静态资源 | `web/public/extensions/<feature>/` | 仅存必须通过公开 URL 访问的资源；可导入资源优先留在功能目录 |
| 定制修改文档 | `docs/customizations/` | 一项功能一份记录，索引只写摘要和链接 |

目前仅前后端扩展主目录与文档目录已建立，表中的功能、配置和资源子目录按需创建。`<feature>` 使用稳定、简短的英文功能名。不要复制整套上游业务，也不预建插件框架或无需求的抽象层。

## 2. 上游只留必要接入点

- 优先复用已有模块接口、鉴权、请求封装和主题能力；定制通过模块调用、路由注册或组件插入接入，业务实现留在扩展目录。
- 后端可在 `router/router.go` 的 `New` 中调用扩展导出的注册函数；需要启动初始化时才在实际启动路径增加调用。导入方向保持清楚：扩展不得反向依赖调用它的 router 或 main 包，以免 Go 导入循环。
- 前端通过功能的明确导出接入已有页面或布局。Next.js 路由约定要求的 `page.tsx`、`layout.tsx`、`route.ts` 留在 `web/src/app/`，只承担框架必要的入口、参数处理和扩展调用，不承载定制业务。这类框架入口是上游“不增加纯转发组件”规则的必要例外。
- 定制 API 默认使用 `/api/extensions/<feature>` 命名空间；选择适当的用户或管理鉴权，保持上游响应约定。不要因为扩展独立就绕过权限、限流或错误处理。
- 每个上游文件改动必须在对应功能记录中写明路径、符号、原因、为何无法仅在扩展内实现，以及同步时的检查点。没有具体功能时不预先修改业务接入点。
- 如果上游缺少必要扩展接口，做最小改动并记录取舍，不通过复制业务、运行时替换或大范围重构规避接入。

## 3. 配置、样式和数据隔离

### 配置

- 定制默认配置和读取逻辑归扩展目录，环境变量统一用 `EXT_<FEATURE>_` 前缀；浏览器可见且非敏感的配置才使用 `NEXT_PUBLIC_EXT_<FEATURE>_`。
- 服务端密钥不得写入前端配置、文档或提交。确需环境变量文件时，在对应配置目录提供 `.env.example`，真实 `.env` 使用已有忽略规则；加载路径在功能文档中写明，不假定框架会自动加载嵌套文件。
- 开关只在功能确需可选时添加，并说明默认值、关闭行为及是否仍需读取数据；不要建立空的开关系统。

### 样式与资源

- 优先使用组件内 Tailwind 类或功能内 CSS Modules；必须覆盖第三方样式时，用该功能独有的根类或 `data-ext-<feature>` 属性限定范围。
- 复用上游主题 token，验证浅色、深色和相关响应式布局。避免无作用域的元素选择器、全局重置或覆盖上游 `globals.css`。
- 资源使用扩展专属路径和文件名；不覆盖上游同名资源。

### 数据

- 默认用 `ext_<feature>_*` 独立表保存定制数据，通过上游记录 ID 关联；不默认给上游表加列、不改其索引和约束，也不把定制数据混入上游配置字段。
- 扩展自行管理表模型及必要的迁移、初始化和版本说明；记录执行时机、重复执行行为、失败处理和回退方式。使用同一数据库即可满足隔离时，不额外引入数据库服务。
- 不可避免的上游表变更必须先解释原因、数据风险与替代方案，获得该变更的明确授权后再执行；同步更新上游数据库说明及功能记录。
- 持久化文件使用 `data/extensions/<feature>/`。浏览器存储使用 `ext:<feature>:` 命名空间，业务数据继续遵循上游的 localforage 约定；清理或重置只操作该功能拥有的数据。

## 4. 提交和修改文档

- 一项功能组织成一个可独立检查、回退的本地提交，包含实现、必要接入、验证和对应文档；较大功能可以拆成有顺序说明的独立提交，不混入其他功能、格式化或依赖升级。
- 建议提交格式为 `feat(ext-<feature>): 描述`、`fix(ext-<feature>): 描述`；规则和目录初始化使用 `docs(extensions): 描述`。上游同步提交与定制功能提交区分。
- 修改前按 [模板](change-template.md) 创建 `docs/customizations/changes/<编号>-<feature>.md`，完成时补全真实结果，并在 [修改索引](changes.md) 登记。不要把计划写成已实现，也不要求在提交内部写入该提交自身的哈希；用记录编号或路径查询 Git 历史。
- 上游 TODO 和待测试文档保留其原意；定制待办、待验证项集中记录在对应功能文档。只有改变上游公共功能时才同步相应公共文档，避免重复维护定制细节。
- 不自动推送、合并远端分支、发布或部署；这些外部操作须有用户明确授权。

## 5. 上游同步和验证

1. 检查 `git status`，确保现有修改已妥善保存；记录当前上游基线和定制提交。不得以同步为由直接清空用户工作。
2. 获取上游更新，在独立的本地同步分支检查差异，再按仓库历史选择合并或变基；不改写已共享历史，远端操作遵守上一节授权边界。
3. 逐项核对修改记录中的上游文件、调用符号、路由权限、导出接口、主题和数据约定；不能仅凭“Git 没冲突”判定兼容。
4. 按实际变更执行相关验证：文档检查链接和一致性，前端检查类型及相关页面，后端检查相关包和接口，数据变更检查迁移与回退；无需对纯文档改动执行全量构建。
5. 在受影响的功能记录里更新结果、未验证项及同步基线。只有完成对应检查才写“通过”。
